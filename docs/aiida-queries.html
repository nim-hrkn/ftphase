AiiDA ジョブの問い合わせ・制御：このプロジェクトで作ったスクリプトと問い合わせ事項

2026-10-23〜25 に ftphase.txdiagram WorkChain（プロファイル ftphase、計算機 mygarden5 / mygarden6 / mygardenx2）を回す中で実際に使った問い合わせと操作を、将来 Claude Cowork から使う AiiDA ジョブ制御用 MCP サーバの設計資料としてまとめる。第 1 節が既存スクリプト、第 2 節が verdi コマンド、第 3 節が Python API の断片、第 4 節が「何を知りたかったか」の一覧、第 5 節が MCP のツール案と安全策。

前提（CLAUDE.md より）：verdi は必ず env/ftphase/bin/verdi -p ftphase（既定プロファイルは別プロジェクトの alamode_pg）。デーモン操作は env/ftphase/bin を PATH に入れてから（daemon restart は停止中だと失敗するので daemon start 2）。プラグインのソースを変えたら pip install -e ./ftphase --no-deps → デーモン再起動 → リモート計算機へ sync_to_host.sh。

2. 使った verdi コマンド

コマンド何を知るため／するために使ったか
process status <pk>WorkChain の木（子 CalcJob の状態と exit code）。先頭行で WorkChain の状態（Waiting [1:run_calculations] / Finished [0] / Finished [401] / Excepted / Killed）、grep -c "Finished \[0\]" で進捗の数え上げ、grep -v "Finished \[0\]" で失敗・待ちだけ抽出
process report <pk>例外のトレースバック（prepare_cells の import エラー、Unrecognized pair style、パーサの exit code 300/320 の理由）
process list [-a -p 1]直近の WorkChain / CalcJob の一覧（pk、経過時間、状態、「Monitoring scheduler: job state QUEUED」など）
process kill <pk...> -F -t 60WorkChain の中止。子 CalcJob と Slurm ジョブは残ることがある（第 4 節）
calcjob outputls <pk> / outputcat <pk> <file> / inputcat <pk> <file>retrieved フォルダの一覧、qha.err・calphy.err・_scheduler-stderr.txt、投入スクリプト _aiidasubmit.sh（gres、conda activate）、input.json・input.yaml（pair_style、cmdargs、lammps_executable）。オプション名は位置引数（-p は無い）
node show <pk>ラベル、計算機、生成時刻
node graph generate <pk> -f svg|png -O file [-a N -d M]provenance 図（WorkChain 全体は 161 ノード・幅 18,000 pt になるので 1 本分を -a 3 -d 2 で描く）。SVG は artifact 添付前に DOCTYPE を削る
daemon status|start N|restart|incr Nワーカー数の確認・再起動（プラグイン更新後）。PATH に verdi が無いと "Unable to find 'verdi' in the path"、停止中の restart は失敗
computer setup|configure core.ssh|test|show|listリモート計算機の登録（paramiko は ssh alias を解決しないので IP、鍵 id_ed25519_aiida、--use-login-shell はフラグ）、6 項目の接続テスト
code create core.code.installed|list|show実行ファイルと prepend（conda activate）の登録、計算機ごとの一覧
config set --append caching.enabled_for aiida.calculations:ftphase.qha / config list cachingCalcJob のキャッシュ有効化（入力が同じ CalcJob は過去の結果を再利用：pk 1128 は 19 本中 16 本をキャッシュ）
profile list|show既定プロファイルの確認（変えない）

3. Python API の断片（verdi より速く・確実）

from aiida import load_profile; load_profile("ftphase")
from aiida.orm import load_node, QueryBuilder, WorkChainNode, CalcJobNode

n = load_node(pk)
n.process_state.value          # created / waiting / running / finished / excepted / killed
n.exit_status                  # 0, 300 (QHA 出力なし), 320 (sweep なし), 401/402 (WorkChain: 子の失敗)
n.label                        # "calphy lqd_x0.10 x=0.1016", "qha s00_fcc fcc x=0.0000"
n.computer.label               # mygarden5 / mygarden6 / mygardenx2
n.get_remote_workdir()         # Slurm ジョブのディレクトリ（ログ・calphy の seg ファイルを直接読む）
n.caller                       # 親 WorkChain（kill 後の孤児判定に使う）
n.base.caching.get_cache_source()   # キャッシュ元ノードの uuid（graph のリンクではない）
n.base.links.get_incoming().all() / get_outgoing().all()   # link_label, node（入力・出力の追跡）

# WorkChain の子 CalcJob を計算機・状態で集計
qb = QueryBuilder().append(WorkChainNode, filters={"id": pk}, tag="w").append(CalcJobNode, with_incoming="w", project=["*"])
# 未終了 CalcJob のうち親が終了済みのもの（孤児）
qb = QueryBuilder().append(CalcJobNode, filters={"attributes.process_state": {"in": ["waiting", "running", "created"]}}, project=["*"])

# 投入（run_aiida.py の中身）

4. 問い合わせ事項の一覧（何を、なぜ知りたかったか）

問い使った手段備考・落とし穴
この WorkChain は終わったか、何本中何本が終わったかprocess status + grep 数え上げ；背景ループで 60〜180 s ごとに確認し、終了語（Finished/Excepted/Killed）で抜ける待ちループが 240 回で時間切れになるので長い待ちは 600 回 × 120 s 等にする
どの子が失敗し、なぜかprocess status で Finished [300/320] を拾う → process report → calcjob outputcat qha.err / calphy.err → get_remote_workdir() で LAMMPS ログ（calphy の seg*.log、averaging.log）を直接読むcalphy の失敗は report.yaml 無し（320）としか出ないので、作業ディレクトリのログが必須
どの計算機で走ったか子 CalcJob の computer.label を集計calcfunction（prepare_cells、assemble）はデーモンのホストで走る
Slurm 側で実際に走っているか・待ちの原因各ホストで squeue -h -o "%i %j %T %M %b"、-t RUNNING、scontrol show node（GRES）ジョブ名 aiida-<pk> で CalcJob と対応づける
kill した WorkChain の残骸aiida_zombies.py（孤児 CalcJob + 終了済みプロセスの Slurm ジョブ）80 本の残骸が両 GPU を数時間塞いだ（2026-10-25）
キャッシュが効いたか、元はどのノードかbase.caching.get_cache_source()、子の状態が投入直後に finished になるかgraph には現れない
provenance が繋がっているかget_incoming/get_outgoing、node graph generate全体図は巨大。1 本分を抜く
投入前に入力が正しいかrun_aiida.py --dry-run（spec、gres、lammps_executable、init_commands、potential_qha の有無）MLIP ごとの分岐が多いので必須
結果の数値fetch_results.py → REPORT.md / summary.json（最低液相温度、純端の融解区間、不変反応、同一相区間）、05 の表から工程別の差（mlip_compare.py）
デーモンは生きているか、ワーカー数daemon status再起動失敗で全 WorkChain が止まっていたことが 1 回

5. MCP サーバのツール案（Claude Cowork 用）

方針：読み取り系は無確認、投入・中止・デーモン操作・scancel は確認付き。プロファイルは引数で明示（既定 ftphase、alamode_pg は読み取りのみ許可）。すべて JSON を返し、長い出力（ログ、graph）はファイルパスを返す。実装は env/ftphase/bin/python から AiiDA API を直接呼ぶ（verdi の subprocess より速く、PATH の問題も避けられる）。

ツール引数返すもの備考
list_workchainsprofile, limit, state, label_containspk, uuid, label, state, exit, created, computer 集計process list 相当
workchain_statuspk状態、子の集計 {finished_ok, failed(exit code 別), waiting, running}, 失敗した子の pk・label、進捗 %process status の構造化
calcjob_detailpklabel, computer, state, exit, scheduler job id/state, remote_workdir, 入力の要点（pair_style, cmdargs, lammps_executable, gres）
calcjob_logpk, file(qha.err|calphy.err|_scheduler-stderr.txt|_aiidasubmit.sh|input.yaml|input.json|remote:<glob>), tailテキスト（末尾 N 行）retrieved に無ければ remote_workdir から読む（calphy の seg ログ）
failure_summarypk失敗した子ごとに report の最後の例外行 + stderr の末尾 + 推定原因（既知パターン：pair style 未認識、MeltedError、virial ゼロ、import エラー）第 4 節の手順の自動化
queuehost(all)各ホストの squeue（running/pending、gres、経過）、GRES の空きssh alias と IP の対応は設定ファイルに
zombiescancel(bool, 要確認)孤児 CalcJob と残骸 Slurm ジョブ；cancel で scancel + killaiida_zombies.py
submit_txdiagramsystem, mlip, computer, qha_computer, smoke, name, extra_spec, dry_rundry_run: spec と入力の要約；本投入: pk, uuid, name（要確認）run_aiida.py をライブラリ化して呼ぶ
killpks, cascade(bool)kill した pk 一覧；cascade で子 CalcJob と Slurm ジョブも要確認。cascade を既定 on にする
fetch_resultspk|name, out_dir出力ファイル一覧と summary.json の要点fetch_results.py
compare_runs[label=pk|dir...]REPORT.md のパスと 06–07 の表mlip_compare.py
cache_infopk子ごとの cache_source（uuid、元 WorkChain）
provenance_graphpk, ancestors, descendants, formatSVG/PNG のパス、ノード数DOCTYPE 除去済み SVG
daemonaction(status|start|restart|incr), workersワーカー数、PIDrestart は停止中なら start に読み替える；要確認
wait_forpks, poll_s, timeout_s終了時の状態（長い待ちはサーバ側でなくクライアントの再呼び出しで）MCP では長時間ブロックしない設計にする
安全策：(1) 書き込み系はすべて確認を要求し、対象 pk のラベルと計算機を表示してから実行。(2) alamode_pg プロファイルとそのデーモンには触れない。(3) kill は必ず cascade（子 CalcJob + scancel）。(4) 投入前に dry_run を強制できるオプション。(5) リモート計算機のパッケージ同期状態（ftphase/src の git hash を各ホストで比較）を queue か submit の事前チェックに含める（古いコピーで QHA が全滅した事例）。
